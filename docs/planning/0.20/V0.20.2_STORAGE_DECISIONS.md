# v0.20.2 Global Tiered Storage Decisions

## Scope

v0.20.2 adds optional project-scoped global storage for archives, derived
artifacts, and caches while preserving the repository-local `.autoforge/`
working set.

## D-20.2.1 — Derive a stable global project identity

Global project storage is keyed by a stable identity derived from the
canonical project path. Display names and aliases must never determine the
storage key.

## D-20.2.2 — Keep active state local

Active configuration, work, decisions, contracts, and governance remain in
the project-local `.autoforge/` directory. Global storage may contain copies,
archives, indexes, and caches, but it cannot become the sole source of truth
for active work.

## D-20.2.3 — Use explicit storage tiers

Each project may use the following global tiers:

- `metadata/` — identity, schema, and capability metadata;
- `active/` — optional derived indexes, never authoritative state;
- `history/` — immutable completed sessions and evidence snapshots;
- `artifacts/` — content-addressed generated artifacts;
- `cache/` — disposable rebuildable data.

## D-20.2.4 — Degrade safely and recover explicitly

If global storage is unavailable, AutoForge continues from local state and
reports degraded storage. Export and import operations must be explicit,
versioned, integrity-checked, and capable of rebuilding global data from the
local project.

## D-20.2.5 — Bound retention and size

History and artifacts obey project retention policies and storage limits.
Pruning must support dry runs, report exact candidates and sizes, and never
remove active local state implicitly.

## Acceptance Criteria

The implementation must define stable paths, a versioned storage manifest,
atomic writes, usage reporting, migration/fallback behavior, export/import
recovery, retention-aware pruning, and focused tests before v0.20.2 release.
