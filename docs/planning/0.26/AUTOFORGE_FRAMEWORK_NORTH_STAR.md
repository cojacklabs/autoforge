# AutoForge Framework North-Star

Status: Authoritative product destination
Established: 2026-08-30
Naming status: AutoForge remains the compatibility name until a separately
approved replacement passes package, executable, repository, domain, legal,
and search-collision review.

## Product Definition

AutoForge is the open-source engineering control plane for AI-assisted
software, data, and AI development.

It preserves project intelligence, resolves the minimum complete context for a
task, governs technical work, coordinates replaceable agents, validates
outcomes, and carries structured learning forward. AutoForge is a framework,
not an AI agent or a general-purpose assistant.

> **Humans think naturally. AutoForge organizes persistently. AI agents execute
> precisely.**

> **AutoForge owns deterministic project intelligence and orchestration—not
> model reasoning or autonomous agency.**

## Responsibility Boundary

```text
Human intent
     |
     v
AutoForge
  Project knowledge + graph + context resolution
  Governance + scope + workflow + validation + evidence
     |
     v
Vendor-neutral agent contract
     |
     +---- Codex / Claude Code / Gemini / Cursor / other agents
     +---- Future CoJack Labs AI
     |
     v
Software / data / AI work -> validated project knowledge
```

AutoForge determines what a request means within a project, what knowledge is
relevant, which constraints apply, what an agent may change, which workflow is
required, and what must be validated. The selected external agent reasons,
generates, and executes within that contract.

## Framework Capabilities

AutoForge supports three compatible modes:

- **Plan:** discovery, research, requirements, specifications, alternatives,
  decisions, roadmaps, and implementation readiness;
- **Build:** scoped context, governance, agent coordination, implementation
  handoff, validation, evidence, and completion;
- **Evolve:** impact analysis, change planning, regression validation,
  observation, learning, and durable knowledge updates.

Its enduring framework domains are:

- repository-native project knowledge and atomic typed artifacts;
- one connected project graph and engineering digital twin;
- explainable, budgeted context resolution;
- constitutions, doctrines, scope, security, and quality governance;
- intent, research, requirements, architecture, domain, data, AI, and design
  specifications;
- work lifecycle, strategy assistance, dependencies, assignments, leases, and
  structured human approvals;
- provider-neutral agent contracts, adapters, handoffs, SDK, CLI, MCP, and
  other interoperability surfaces;
- traceability, change impact, validation evidence, release readiness, and
  engineering learning;
- global project discovery and portable project continuity without silently
  authorizing access across repositories.

## Canonical Project Model

The repository is the project brain. AutoForge maintains one connected project
model rather than separate competing graphs for governance, domain, design,
architecture, traceability, and the digital twin.

Tracked, reviewable Markdown and JSON remain canonical project truth. A local
database may accelerate search, graph traversal, status projections, or safe
coordination only when its state is rebuildable or its operational lifecycle is
explicit. No projection may silently become the sole copy of durable project
knowledge.

Raw conversations, hidden model reasoning, credentials, provider caches, and
ephemeral run logs are not project memory by default. Promoted knowledge needs
provenance, scope, authority, lifecycle, and export behavior.

## Human Authority

AutoForge may automate deterministic mechanics and coordinate approved agent
work, but automation is not unrestricted autonomy. Humans remain responsible
for goals, strategy, consequential permissions, accepted tradeoffs, and release
authorization.

Model output is a proposal until applicable schema, governance, scope,
approval, validation, and evidence requirements are satisfied. An adapter must
not claim enforcement stronger than the host agent actually supports.

## Relationship to the Future CoJack Labs AI

A separately named CoJack Labs AI may eventually own general conversation,
personal memory, broad research, model routing, cross-application action, and a
visual prompt-to-product workspace. It may consume AutoForge whenever technical
project work requires governed context and validation.

AutoForge must remain independently installable and usable by humans and any
compatible agent. The future AI must not own a competing copy of canonical
project truth. Product ideas separated from this framework are preserved in
[Separated Future AI Product Portfolio](./SEPARATED_FUTURE_AI_PRODUCT_PORTFOLIO.md).

## Explicit Non-Goals

AutoForge is not:

- a general-purpose or personal AI assistant;
- a proprietary model or model-routing product;
- an autonomous software developer;
- a first-party conversational coding agent;
- a hosted-only prompt-to-application platform;
- a visual canvas or IDE;
- the owner of general personal memory, email, messaging, or SaaS actions;
- dependent on one model, provider, agent, cloud account, or hosted service.

AutoForge may define contracts, governance, and adapters used by those systems
without becoming those systems.

## Architectural Invariants

1. AutoForge remains deterministic, provider-neutral, repository-native, and
   locally useful.
2. Project intelligence belongs to the project.
3. The Git repository root is the canonical project boundary.
4. Global registration and cross-project access are explicit.
5. Knowledge storage, graph relationships, and context resolution are separate
   responsibilities over one project model.
6. Context packets provide minimum complete context, not maximum context.
7. Agents remain replaceable and receive versioned, scoped contracts.
8. Humans govern strategy and consequential authority.
9. Validation and evidence precede completion and release claims.
10. Software, data, and AI engineering remain first-class domains.
11. External products consume supported interfaces and cannot create a second
    source of project truth.
12. Naming changes require a separate compatibility and collision decision.

## Success Test

AutoForge succeeds when a human can open a technical repository with any
compatible agent and the project itself can explain what is being attempted,
what is already known and decided, what is affected, which rules apply, what
may change, what evidence is required, and how another participant can continue
without rediscovery.

The framework is not measured by how convincingly it chats. It is measured by
whether technical work remains understandable, governed, portable, verifiable,
and continuous across agents and time.
